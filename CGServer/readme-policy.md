# 송출 틱/타임스탬프 정책 (확정 사항)

작성일: 2026-10-05 (개정: fps 틱 방식 폐기, 입력 도착 구동으로 변경)

## 확정된 정책

| # | 항목 | 정책 |
|---|---|---|
| P1 | 기준 시각 | 영상·음성이 공통 `t0` 하나를 쓴다. 한 번 정하면 바꾸지 않는다. (GStreamer 의 `base_time`) |
| P2 | fps 틱 사용 안 함 | 지금처럼 fps 틱(타이머)으로 프레임을 만들지 않는다. (확정 2026-10-05) |
| P3 | 입력 버퍼 | CEF, 미디어, 라이브 입력을 각자의 PTS(시간 정보)와 함께 버퍼에 **도착하는 대로 계속 쌓는다.** (확정 2026-10-05) |
| P4 | 인코딩 시점 | 입력이 **들어오는 대로 무조건** 인코더에 넣는다. 도착한 입력은 조건 없이 모두 인코딩하며, 건너뛰거나 버리지 않는다. 단, 영상 소스가 있는 구간의 인코딩 기준은 P15 를 따른다. (확정 2026-10-05) |
| P5 | 송출 | 인코더에 설정된 **bitrate 기준**으로 송출한다. 인코딩된 데이터를 송신 큐에 넣고, 송신 스레드가 목표 bitrate 에 맞춰 패킷을 일정한 간격으로 내보낸다. (확정 2026-10-05, 앞선 "송신은 bitrate 페이싱" 안을 이어받음) |
| P6 | 인코더 bitrate | 인코더의 bitrate 를 설정한다. (확정 2026-10-05, 설정 방법은 미정) |
| P7 | 드롭 | EncodeLoop(소스)에서는 프레임을 버리지 않는다. 드롭 판단은 하류(UDP 수신 단말)의 몫이다. 기존 UI 지터 버퍼의 오버플로 drop 은 별개의 앞단 로직이라 그대로 둔다. |
| P8 | 오디오 | 블록 `n` 의 시각/PTS 를 `t0 + n × 1024/48000` 으로 둔다. (`audio_mixer.cpp` 가 이미 이 방식, 공통 `t0` 만 공유) |
| P9 | 라이브 입력 영상 PTS | HDMI-RX(V4L2) 프레임의 PTS 는 **캡처 당시의 시간 정보**(V4L2 버퍼 타임스탬프)로 설정한다. 공통 `t0` 기준 시간축으로 환산해 쓴다. (확정 2026-10-05) |
| P10 | 라이브 입력 오디오 PTS | HDMI 입력 음성(ALSA 캡처)의 PTS 는 **캡처 당시의 시간 정보**(ALSA 캡처 타임스탬프)로 설정한다. 공통 `t0` 기준 시간축으로 환산해 쓴다. (확정 2026-10-05) |
| P11 | 미디어 파일 재생 PTS | 미디어 파일(영상·음성)을 재생할 때의 PTS 는 **파일에 들어 있는 시간 정보**(컨테이너의 PTS/DTS)를 기준으로 한다. 공통 `t0` 기준 시간축으로 환산해 쓴다. (확정 2026-10-05) |
| P12 | CEF(UI) 그림 | CEF 그림의 시간 정보는 **`OnPaint` 로 입력된 시각**으로 한다. 다른 입력(P9~P11)과 같이 "입력된 시각"을 가진 소스로 취급하고, 공통 `t0` 기준 시간축으로 환산해 쓴다. (확정 2026-10-05) |
| P13 | 출력 PTS | 출력 PTS 는 **입력 시의 timestamp** 로 한다. 인코더에 넣은 입력의 시간 정보(P9~P12)가 그대로 출력 PTS 가 된다. 프레임 카운터(`n_`) 기반 PTS 는 쓰지 않는다. (확정 2026-10-05) |
| P14 | 합성 프레임의 출력 PTS | 합성 프레임의 출력 PTS 는 **영상 소스(라이브 또는 파일)가 있으면 영상의 timestamp**(P9, P11)를 쓰고, **영상이 없는 CG 구간에서는 CEF 의 입력 시각**(P12)을 쓴다. 영상 프레임이 합성의 기준이 된다. (확정 2026-10-05) |
| P15 | 영상 구간의 인코딩 기준 | 영상 소스(라이브 또는 파일)가 있는 구간에서는 **영상 프레임이 도착할 때 인코딩**한다. 이때 CEF 는 그 시점의 최신 그림을 합성에 쓴다. CG 만 있는 구간에서는 CEF 그림이 도착할 때 인코딩한다(P4). 따라서 CEF 60 + 영상 60 이 동시에 와도 인코딩은 영상 도착 횟수(60)만큼이다. (확정 2026-10-05) |

## 폐기된 정책 (fps 틱 방식)

| 항목 | 내용 | 폐기 사유 |
|---|---|---|
| 대기 시각 | `due(n) = t0 + scale(n, 1e9 / fps)` | P2: fps 틱 사용 안 함 |
| 영상 PTS | `pts(n) = scale(n, 90000 / fps)` (틱 번호 기반) | P2 |
| 격자 유지 | 늦어도 격자를 옮기지 않음 | P2 |
| 늦은 틱 | 연속 따라잡기 | P2 |
| CFR | 밀린 틱을 직전 그림 중복으로 채워 틱마다 패킷 1개 | P4: 도착할 때마다 인코딩 |
| 프레임 생성과 송신의 분리 | 생성은 fps 틱, 송신은 bitrate 페이싱 | 생성 방식이 P4 로 바뀜. 송신은 P5 로 유지 |

## 결정되지 않은 목록

| # | 항목 | 내용 | 상태 |
|---|---|---|---|
| U1 | 정지 화면 (CG 만 있는 구간) | CEF 는 화면에 변화가 없으면 `OnPaint` 를 호출하지 않는다 (`readme-history-d11.md:748` "정적 화면은 paint=0/s", `main.cpp:586` 주석). P4 로는 CG 만 있고 정지일 때 인코딩이 일어나지 않아 송출이 끊긴다. 영상(라이브/미디어) 구간은 프레임이 계속 도착하므로 해당 없음. 직전 프레임 재인코딩(하한 간격)으로 유지할지, 멈출지는 미정 | **테스트 예정** (현재 gles-egl 경로에서 정지 화면 paint 측정) |
| U2 | 인코더가 입력을 못 따라갈 때 | P4(무조건 인코딩)와 P7(드롭 없음)이 겹치면 입력 큐가 계속 쌓여 지연과 메모리가 무한히 커질 수 있다 (입력 1장 약 8MB, `main.cpp:164`). 대응: 인코더 2개를 두고 GOP 단위로 나눠 인코딩한 뒤 재정렬해서 mux 로 전송 (프레임 단위 번갈아 인코딩은 참조가 어긋나 불가). 입력은 최대 1080p60 전제 | 방향 확정, 정책 반영 전. **4K 인코더에 이미 구현돼 있다고 함** — 이 저장소 `src/cg-streamer` 에서는 찾지 못함 (인코더 `g_encoder` 1개, 스레드 1개). 구현 위치 확인 필요 |
| U4 | 인코더 설정과 불규칙한 도착 | `gop = fps`(IDR 이 "fps 프레임마다")와 고정 fps 전제의 rate control (`fps_in_flex = 0`) 이 도착이 불규칙하면 어긋날 수 있다. MPP 는 입력 PTS 를 그대로 출력에 복사하고 프레임 간격을 만들어 주지 않음을 소스에서 확인 (`mpp_enc_impl.c`). `fps_in_flex` 의 정확한 효과는 미확인 | 미정 |
| U5 | 수신 단말의 가변 프레임레이트 수용 | 도착 구동이면 출력이 가변 프레임레이트가 된다. 수신 단말이 PTS 간격이 불규칙한 TS 를 받아들이는지 확인한 적 없음 | 미확인 |
| U6 | 출력 fps 규칙 재확인 | 이전 확정(2026-10-05): 라이브가 30fps 면 출력 30fps, 60fps 면 출력 60fps / 미디어 파일은 출력 fps 와 같은 fps 의 파일만 등록. 도착할 때마다 인코딩하면 출력 fps 가 입력 도착 간격으로 정해지므로 이 규칙이 그대로 유효한지 | 재확인 필요 |
| U7 | 인코더 bitrate 설정 방법 | P6 은 확정이나 현재 `kBitrate` 가 8Mbps 상수 (`main.cpp:90`)이고 `cgsetup.cfg` 항목이 없음. 송신 페이싱(P5) 속도 여유(`bps_max` 1.0625배, TS 오버헤드, 오디오 128kbps)도 미정 | 미정 |

## 채택하지 않은 것
